# 动态监控与企业微信定时生命周期设计

## 目标

把当前已经验证的动态补偿逻辑纳入 Windows 计划任务，使动态监控和企业微信长连接机器人在同一个时段任务中启动，并在该时段动态窗口结束后共同退出。

## 已确认的业务规则

- 动态窗口仍由签到窗口扩展得到：签到窗口为预约开始前 30 分钟至开始后 15 分钟，动态窗口默认再向前扩展 30 分钟、向后扩展 90 分钟。
- 以预约开始时间 `08:00` 为例，动态窗口是 `07:00-09:45`，任务必须覆盖完整的 165 分钟。
- 动态边界提前 2 分钟检查；迟到时每 30 分钟按“当前”取消并重新预约；最终边界仍未入馆时取消预约。
- 暂离判断继续使用“我的预约”记录中的 `awayBegin/awayEnd`，并保留普通 30 分钟、餐时 90 分钟规则。
- 启用时段超过 3 个时，动态补偿不启动。

## 架构

### 计划任务

`scripts/install-task.ps1` 继续安装静态预约任务，同时为每个启用的动态补偿时段安装一个隐藏任务。动态任务调用统一入口：

```text
python -m scripts.run_dynamic_monitor --period <period> --run-for-minutes <duration>
```

安装器根据账号初始化配置和动态窗口参数计算任务起止：

- 同一时段多个账号时，启动时间取最早动态窗口开始时间；
- 结束时间取最晚动态窗口结束时间；
- 运行时长为上述起止时间差，默认单账号标准窗口为 165 分钟；
- 动态窗口跨午夜或配置无法解析时，不注册该动态任务并输出明确错误。

动态任务使用隐藏执行、联网后启动、可唤醒、允许电池运行和 `IgnoreNew` 并发策略。静态预约任务和动态任务使用不同名称，卸载时一起移除。

### 统一生命周期入口

`run_dynamic_monitor.py` 增加时段筛选、最大运行时长和机器人托管能力：

1. 读取本地预约状态并创建或恢复该时段的 `dynamic_sessions`。
2. 确认存在可监控预约后，启动一个企业微信机器人子进程。
3. 监控循环只处理指定时段，持续到任务截止时间或该时段会话全部进入终态。
4. 监控正常结束、异常退出、认证重试耗尽或收到停止信号时，在 `finally` 中关闭机器人子进程。
5. 机器人已经由其他动态任务占用时，不重复启动第二个机器人；监控仍可继续执行。

机器人通过现有 `--run-for-minutes` 机制运行，但其时长由监控入口统一计算和控制，不再由独立的固定机器人计划任务控制。

### 数据和真实状态

- `dynamic_sessions` 保存跨进程、跨重启的监控进度、窗口和最近检查时间。
- `dynamic_cancellations` 负责取消动作幂等和每日 15 次限制。
- 预约是否存在、`CHECK_IN/COMPLETE/RESERVE` 状态以及暂离字段仍以浏览器会话读取的学校接口为准。
- 任务重启后继续使用数据库中的 `action_index`，不会重复已完成的迟到补偿动作。
- 查询失败或认证失效时保留当前预约并进入安全保持；机器人清理失败只记录日志，不覆盖监控结果。

## 配置边界

- 动态窗口范围、轮询间隔、边界提前量、迟到重约间隔和每日取消上限继续使用 `.env` 中现有配置。
- `accounts.json` 中的时段窗口和默认到馆时间用于安装器计算动态任务起止。
- 当前启用一个账号和三个标准时段；第 4、5 段保留代码支持但默认关闭。
- 手动预约在动态任务已经运行期间可以自动纳入对应时段；如果手动预约发生在任务结束后，不承诺自动唤醒已结束的动态任务。
- 企业微信控制命令仍然要求动态监控任务在运行；机器人只负责接收和排队，实际取消由监控入口执行。

## 测试策略

- 为任务生命周期增加测试：动态任务参数包含时段、完整窗口时长和机器人托管标志。
- 为入口增加测试：机器人在监控结束和异常路径均被终止，重复启动不会创建第二个机器人。
- 为安装器增加静态检查：动态任务名称、动作参数、旧的独立机器人任务移除和完整窗口计算逻辑存在。
- 保留现有预约、动态补偿、会话重建、企业微信和数据库测试，并运行全量 pytest、Python 编译检查和 PowerShell 解析检查。

## 不在本次范围

- 不改变学校预约接口、门禁接口或状态字段映射。
- 不把企业微信控制命令扩展为新的命令集合。
- 不修改产品期望文档、账号凭据、数据库内容或浏览器资料目录。

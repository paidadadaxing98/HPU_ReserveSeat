# v0.8 账号初始化与定时预约设计

## 目标

在现有多账号、浏览器会话隔离、登录验证码识别和预约查询能力之上，增加一次性的账号初始化入口，让每个账号在进入调度器前完成登录和接口能力确认；同时把定时任务、真实预约执行和企业微信机器人通知连接成一条可追踪的运行链路。

初始化命令只验证登录、座位系统首页和“我的预约”接口，不选择座位、不点击预约、不提交任何预约。

## 范围与边界

本次 v0.8 包含：

- `scripts/initialize_account.py --account <accounts.json 中的 id>` 交互式初始化命令；
- 初始化状态、接口能力和最后验证时间保存到账号独立数据库；
- 学习窗口和座位偏好写回 `accounts.json` 对应账号的 `initialization` 节点；
- 调度器运行前检查账号是否已完成初始化，未完成时安全跳过并发送原因；
- 调度器调用统一的预约执行入口，保留 dry-run 和真实提交模式；
- 定时运行结果按账号推送到企业微信群机器人；
- 更新 `README.md` 和本地 `产品期望.md`，其中 `产品期望.md` 继续由 Git 忽略。

本次不包含：

- 企业微信机器人接收消息、自然语言指令、企业微信小程序双向控制；
- 把校园账号、Cookie、浏览器目录或数据库上传到云端；
- 初始化过程中的任何真实预约或取消预约；
- 在没有真实页面证据时假设网站存在某个随机派位按钮。

## 配置模型

### 学习窗口

账号的 `initialization.periods` 继续使用现有 `arrival_window`、`departure_window` 和 `default_arrival` 字段，保持旧配置兼容，但默认值调整为三个学习窗口：

| 时段 | 到馆窗口 | 离馆目标 | 默认预计到馆 |
|---|---|---|---|
| 上午 | `08:00-12:00` | `12:00` | `08:30` |
| 下午 | `14:30-18:30` | `18:30` | `15:00` |
| 晚上 | `19:30-22:00` | `22:00` | `20:00` |

窗口是可接受的学习时间范围，不是必须原样提交的固定预约。例如上午可以根据预计到馆时间生成 `08:30-12:00`，实际开始和结束时间仍按网站可选项、30 分钟粒度和最多 4 小时规则校验。

初始化命令支持交互式修改三个窗口，也支持用重复参数预先提供窗口：

```text
--period morning=08:00-12:00
--period afternoon=14:30-18:30
--period evening=19:30-22:00
```

未提供任何窗口时展示上述默认值；只提供部分窗口时，未提供的时段使用默认值。命令行窗口优先于原有 `accounts.json` 配置，交互确认后的最终值写回文件。

### 座位偏好

`initialization.seat_preference` 保存一次初始化选择：

```json
{
  "mode": "random"
}
```

可选模式为：

- `random`：从预约时实际读取到的可用座位中随机选择；
- `floor`：保存用户选择的楼层，预约时只在该楼层的可用座位中选择；
- `seats`：保存用户输入的座位号优先列表，按列表顺序尝试。

初始化向导先读取并展示当前可见的阅览室、楼层和座位信息，再让用户选择模式。指定座位号不要求初始化时占用座位；初始化只验证接口并保存偏好。楼层模式保存楼层标识，预约时由布局数据确认座位所属楼层，无法确认楼层时停止而不提交。

为兼容已有配置，旧的 `initialization.preferred_seats` 仍可读取；加载时转换为 `seat_preference.mode=seats`。新向导写入 `seat_preference`，不删除旧字段，避免旧脚本失效。

## 初始化流程

1. 根据 `--account` 选择 `accounts.json` 中 `enabled: true` 的账号 ID；多账号时缺少参数立即报错，禁用账号不可运行。
2. 创建账号独立目录、账号锁、持久化浏览器会话和数据库。
3. 打开座位系统入口，复用已有会话；会话失效时使用账号凭据和验证码流程登录。
4. 只在最终确认进入座位系统首页后继续。
5. 捕获可重放的页面 API 认证信息，调用“我的预约”历史接口和当前预约接口；至少一个接口成功返回合法结构并确认认证可用，才记录 `my_reservations` 能力为 `true`。
6. 读取座位系统首页可用于初始化的阅览室/座位信息，展示交互式窗口和座位偏好选择。
7. 将最终学习窗口和座位偏好写回 `accounts.json`，在数据库保存初始化结果、能力清单、验证时间和安全摘要。
8. 输出账号 ID、窗口、座位偏好、接口能力和下一步可运行命令；流程中不点击座位、不打开时间弹窗、不点击“立即预约”。

如果登录、首页确认或“我的预约”接口验证失败，初始化状态保持未完成；偏好可以不写入，或只在用户确认后写入，调度器不得使用该账号执行预约。

## 状态存储

账号独立数据库增加初始化状态表，至少包含：

- `account_id`；
- `status`：`pending`、`ready` 或 `failed`；
- `login_verified`；
- `home_verified`；
- `my_reservations_verified`；
- `capabilities` JSON；
- `last_verified_at`；
- `message`。

`ready` 只有在登录、座位系统首页和“我的预约”接口均验证成功后才能写入。重新运行初始化命令覆盖上一次验证结果；数据库写入失败或账号锁冲突时不报告为成功。

## 调度与预约

调度器在每个账号任务开始前读取初始化状态：

- `ready`：进入预约流程；
- 其他状态：输出“请先初始化账号”的明确原因，记录一次跳过结果，不进入阅览室、座位或提交流程。

调度器继续按前一天 `19:30` 规划次日预约，账号之间串行执行并保留配置的等待间隔。每个账号每天最多提交一个有效预约。预约执行器读取账号学习窗口和座位偏好，计算一个符合窗口、网站选项、半小时粒度和 4 小时上限的具体时间；页面或接口校验失败时停止，并将失败原因交给通知层。

现有预览脚本中的登录、接口认证、座位布局、开始/结束时间验证和提交后核验逻辑抽取为可复用的预约执行边界。脚本继续支持预览、调试确认和真实提交；调度器使用同一边界，避免两套流程产生不同结果。

## 企业微信通知

本阶段沿用企业微信群机器人 Webhook，按账号使用账号配置的 Webhook，未配置时静默运行。通知至少覆盖：

- 初始化成功、初始化失败；
- 调度跳过未初始化账号；
- 预约成功；
- 明确失败；
- 提交后待核验或结果不明确；
- 调度器账号运行异常。

消息包含账号 ID、日期、时段、预约时间、阅览室/座位（已知时）和下一步提示。通知发送失败不改变预约结果、不触发重试，不把 Webhook 或账号密码写入日志。

## 测试策略

- 配置测试覆盖默认窗口、部分窗口覆盖、命令行窗口解析、座位偏好三种模式和旧字段兼容；
- 存储测试覆盖初始化状态新建、更新、读取和失败状态；
- 初始化逻辑测试覆盖只验证接口、不调用预约/取消方法，以及未完成状态的安全停止；
- 调度测试覆盖 ready 账号运行、未初始化账号跳过、多账号串行和通知摘要；
- 企业微信测试覆盖初始化/调度消息格式、Webhook 未配置和发送异常隔离；
- 全量运行现有 pytest、编译检查和命令帮助检查。

## 验收标准

以下命令可执行并产生明确结果：

```powershell
.\.venv\Scripts\python.exe scripts\initialize_account.py --account account02
.\.venv\Scripts\python.exe scripts\test_login.py --account account02
.\.venv\Scripts\python.exe scripts\diagnose_login.py account02
```

初始化完成前，定时预约不会访问选座或提交接口；初始化完成后，调度器能读取初始化状态并按账号偏好执行。README 的“快速开始”包含多账号 ID 规则、登录、诊断、预览、调试提交、真实提交和结束时间采集命令。
